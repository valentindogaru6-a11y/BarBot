# BarBot

BarBot — Telegram-справочник для сотрудников бара. Категории и позиции
полностью формируются из `data/catalog.json`: новую категорию, напиток,
десерт или рабочий стандарт можно добавить без изменения Python-кода.

Текущая версия использует Python 3.12, aiogram 3 и Telegram long polling.
Каталог хранится в JSON и валидируется Pydantic. Пользователи и изменяемые
роли хранятся в локальной SQLite, а владельцы экземпляра задаются по
Telegram user ID через окружение.

## Возможности

- главное inline-меню: «📚 Каталог» и «🔍 Поиск»;
- динамические категории, подкатегории и позиции;
- один необязательный уровень подкатегорий с сортировкой и `is_active`;
- пагинация по 8 элементов;
- универсальные карточки с составом, характеристиками, шагами и тегами;
- отправка фотографии по Telegram `file_id`;
- поиск по названию, описаниям, тегам и ингредиентам;
- локальный голосовой поиск через Vosk без внешних STT API;
- FSM-диалог поиска с командой `/cancel` и inline-отменой;
- роли `super_admin`, `admin`, `bartender`, `accountant`, `user` и `blocked`;
- локальная SQLite-база пользователей и управление ролями;
- feature-flagged Telegram UX для складских списаний и перемещений;
- предварительные и финальные складские XLSX-отчёты с историей;
- защищённая Telegram-админка для каталога, текстов и фотографий;
- атомарная запись, резервные копии и JSONL-аудит;
- понятные сообщения при ошибках файла или структуры каталога.

## Архитектура

```text
data/catalog.json          data/barbot.db
       ↓                         ↓
JSON storage              SQLite users + warehouse foundation
       └──────────┬──────────────┘
                  ↓
app/models → app/services → app/handlers → app/keyboards
```

Основные каталоги:

- `app/models/` — модели каталога, пользователей, ролей и warehouse domain;
- `app/storage/` — JSON-каталог и SQLite без ORM;
- `app/services/` — каталог, поиск, авторизация, CRUD и аудит;
- `app/handlers/` — пользовательские сценарии и разделённый пакет `admin/`;
- `app/keyboards/` — пользовательские и административные callbacks/клавиатуры;
- `app/utils/` — нормализация и безопасное HTML-форматирование;
- `data/catalog.json` — данные каталога;
- `tests/` — тесты без обращений к Telegram API.

`data/users.json` не используется и оставлен только как deprecated-файл.
Источник пользователей и изменяемых ролей — `data/barbot.db`.

## Создание Telegram-бота

1. Откройте официальный аккаунт `@BotFather` в Telegram.
2. Выполните команду `/newbot`.
3. Укажите отображаемое имя и уникальное имя, оканчивающееся на `bot`.
4. Сохраните выданный токен. Не публикуйте его и не добавляйте в Git.

## Установка

```bash
cd /opt/barbot
python3.12 -m venv .venv
source .venv/bin/activate
python -m pip install -r requirements.txt
```

`XlsxWriter>=3.2,<4` является runtime-зависимостью для складских отчётов.
Pandas и Excel-reader библиотека приложению не требуются.

## Настройка `.env`

Скопируйте безопасный пример:

```bash
cp .env.example .env
```

Заполните значения:

```dotenv
BOT_TOKEN=replace_with_your_telegram_bot_token
CATALOG_PATH=data/catalog.json
DATABASE_PATH=data/barbot.db
SUPER_ADMIN_IDS=[123456789,987654321]
WAREHOUSE_ENABLED=false
WAREHOUSE_REPORTS_PATH=reports/warehouse
```

- `BOT_TOKEN` обязателен.
- `CATALOG_PATH` необязателен и по умолчанию указывает на
  `/opt/barbot/data/catalog.json`.
- Относительный `CATALOG_PATH` всегда вычисляется от корня проекта, поэтому
  запуск не зависит от текущей рабочей директории.
- `DATABASE_PATH` по умолчанию равен `/opt/barbot/data/barbot.db` и также
  вычисляется от корня проекта.
- `SUPER_ADMIN_IDS` — необязательный JSON-массив положительных Telegram ID.
  Для production рекомендуется указать минимум одного владельца.
- `WAREHOUSE_ENABLED` по умолчанию равен `false`. Значение `true` подключает
  складской router, кнопку и команду `/warehouse`; оно не импортирует seed и
  не создаёт складскую номенклатуру автоматически.
- `WAREHOUSE_REPORTS_PATH` — относительный от корня проекта каталог финальных
  XLSX; по умолчанию `/opt/barbot/reports/warehouse`. Абсолютные пути и выход
  за пределы проекта запрещены. Каталог создаётся только при генерации.
- Если `SUPER_ADMIN_IDS` не задан, старый `ADMIN_IDS` временно используется
  как bootstrap владельцев. Это deprecated-совместимость; предупреждение
  пишется без вывода самих ID.

Настоящий `.env` исключён из Git.

## Voice Search

Бот принимает обычные Telegram voice messages, локально преобразует OGG/Opus
через `ffmpeg` в mono PCM WAV (16 bit, 16 kHz) и распознаёт русскую речь
локальной моделью Vosk. Аудио и текст распознавания не отправляются во внешние
STT API. Временные OGG/WAV удаляются после каждого запроса, транскрипт не
попадает в audit и по умолчанию не записывается в log.

Голосовой запрос можно сформулировать свободно: «найди Old Fashioned»,
«покажи мне киви панч», «открой тех карту пэ эф клубника». Служебные слова
убираются детерминированно, после чего fuzzy-matcher сравнивает запрос с
активными названиями, `voice_aliases`, тегами и обычными поисковыми полями.
Уверенное совпадение открывает существующую карточку с фото и доступной
администратору кнопкой редактирования; при нескольких вариантах бот показывает
обычные inline-кнопки результатов поиска.

Настройки:

```dotenv
VOICE_SEARCH_ENABLED=true
VOSK_MODEL_PATH=models/vosk-model-small-ru-0.22
VOSK_LANGUAGE=ru
VOICE_MAX_DURATION_SECONDS=30
VOICE_MAX_FILE_SIZE_MB=10
VOICE_MAX_CONCURRENT=1
VOICE_DEBUG_TRANSCRIPTS=false
```

`VOSK_MODEL_PATH` вычисляется от `/opt/barbot` и должен оставаться внутри
проекта. Модель загружается лениво при первом голосовом
запросе и затем переиспользуется. По умолчанию одновременно выполняется только
одно распознавание, чтобы не перегружать VPS. Если grammar, построенная из
активных названий и алиасов каталога, не поддерживается конкретной моделью,
сервис автоматически использует ту же модель без grammar.

Для неоднозначных названий можно вручную добавить необязательное поле, не
меняя стабильный `id`:

```json
{
  "id": "old-fashioned",
  "name": "Old Fashioned",
  "voice_aliases": ["олд фэшн", "олд фешн"]
}
```

Отсутствующее поле совместимо со старым каталогом и означает пустой список.
Приложение не переписывает `catalog.json` ради добавления этого значения.

### Установка на Ubuntu/VPS

Модель не входит в репозиторий и не скачивается приложением. Установите
системные пакеты, Python-зависимости и официальную малую русскую модель Vosk
вручную:

```bash
cd /opt/barbot
sudo apt update
sudo apt install -y ffmpeg unzip curl
.venv/bin/python -m pip install -r requirements.txt
mkdir -p models
curl -fL \
  -o /tmp/vosk-model-small-ru-0.22.zip \
  https://alphacephei.com/vosk/models/vosk-model-small-ru-0.22.zip
unzip /tmp/vosk-model-small-ru-0.22.zip -d models
rm /tmp/vosk-model-small-ru-0.22.zip
```

Официальный список и характеристики моделей опубликованы на странице
[Vosk Models](https://alphacephei.com/vosk/models). Каталог модели должен
получиться как `/opt/barbot/models/vosk-model-small-ru-0.22/`; его бинарное
содержимое исключено из Git.

Проверьте окружение без запуска Telegram polling:

```bash
cd /opt/barbot
.venv/bin/python scripts/check_voice_dependencies.py
```

Скрипт только проверяет `ffmpeg`, импорт Python-пакета, структуру каталога
модели и доступную RAM; он не читает `.env`, не загружает модель и ничего не
изменяет. После ручной установки зависимостей или изменения voice-настроек
нужно перезапустить действующий service обычной процедурой владельца. В рамках
разработки и тестов polling/systemd не запускаются.

Малая русская модель занимает около 45 МБ на диске, а малые модели Vosk обычно
требуют порядка 300 МБ RAM во время работы. Для небольшого VPS разумно иметь не
менее 512 МБ свободного запаса и оставить `VOICE_MAX_CONCURRENT=1`. Рост
параллелизма увеличивает CPU/RAM-нагрузку.

Если голосовой поиск сообщает о временной недоступности, проверьте по порядку:

- `ffmpeg` доступен в `PATH` пользователя systemd-service;
- пакет `vosk` установлен именно в `/opt/barbot/.venv`;
- распакованный каталог совпадает с `VOSK_MODEL_PATH` и содержит `am/` и
  `conf/`;
- процесс имеет право читать каталог модели и достаточно памяти;
- лимиты длительности и размера не меньше параметров присланного voice.

### Voice Aliases

Русская модель Vosk обычно возвращает англоязычные названия русской
фонетикой. Поэтому перед fuzzy-сопоставлением BarBot строит лёгкие runtime
aliases для любой активной `CatalogItem`, независимо от категории:

```text
киви панч       → Kiwi Punch
порнстар герл   → Pornstar Girl
блэк хайв       → Black Hive
олд фэшн        → Old Fashioned
```

Alias-service объединяет нормализованное display name, ручные
`voice_aliases`, несколько детерминированных Latin → Cyrillic вариантов и
небольшой общий словарь барных/продуктовых исключений. Пунктуация, регистр,
Unicode-варианты и лишние пробелы нормализуются. Генерация ограничена малым
числом вариантов и кешируется по ID, имени и ручным aliases; дополнительная
Vosk/ML-модель не загружается.

Matcher берёт лучший score среди всех aliases, тегов и существующих поисковых
полей. Полное уверенное название сразу открывает карточку. Общая часть вроде
«порнстар» оставляет несколько близких результатов и показывает inline-кнопки
`Pornstar Girl`, `Pornstar Boy` и `Pornstar Strawberry`.

Ручные варианты можно сохранять через секцию полного шаблона карточки:

```text
ГОЛОСОВЫЕ АЛИАСЫ:
киви панч
киви пунч
киви панц
```

Один alias указывается на строку. Runtime-генерация сама `catalog.json` не
изменяет. Проверить сгенерированные варианты для всех активных карточек или
увидеть TOP-10 fuzzy-результатов можно без Telegram, Vosk и `ffmpeg`:

```bash
/opt/barbot/.venv/bin/python scripts/debug_voice_aliases.py
/opt/barbot/.venv/bin/python scripts/debug_voice_aliases.py "киви панч"
/opt/barbot/.venv/bin/python scripts/debug_voice_aliases.py "порнстар"
```

## Роли и безопасность

- `super_admin` задаётся только через `SUPER_ADMIN_IDS`, имеет все права,
  назначает и снимает `admin` и не может быть изменён через бота;
- `admin` управляет каталогом и пользователями, назначает `bartender`,
  `accountant`, меняет `user/bartender/accountant/blocked`, но не управляет
  admin/super_admin и собой;
- `bartender` использует каталог и поиск без административных функций;
- `accountant` (Бухгалтер) пока имеет только `/start`, `/help` и `/myid`;
  каталог, поиск, голосовой поиск и административные функции ему недоступны;
- `user` имеет обычный доступ к каталогу и поиску;
- `blocked` видит только сообщение об ограничении, `/help` и `/myid`.

Разрешения вычисляются централизованно и повторно проверяются перед сменой
роли. Super Admin не хранится как изменяемая SQLite-роль и потому не может
быть понижен или заблокирован через Telegram.

Узнать собственный Telegram ID можно командой:

```text
/myid
```

Добавьте полученное число в `.env`, например:

```dotenv
SUPER_ADMIN_IDS=[123456789,987654321]
```

Не используйте username, имя или номер телефона вместо ID. Проверка прав
выполняется не только при построении меню, но и в каждом административном
callback, message handler и FSM-шаге. Прямая попытка открыть callback
возвращает «Недостаточно прав».

После изменения `.env` требуется restart процесса/systemd. Настоящие ID не
следует добавлять в README или `.env.example`.

## Запуск

Активируйте виртуальное окружение и запустите:

```bash
source .venv/bin/activate
python -m app.bot
```

При запуске бот отключает webhook без удаления накопившихся обновлений и
переходит в long polling.

## Telegram Commands

При запуске бот регистрирует официальные Bot Commands и включает встроенную
кнопку команд Telegram. Основной интерфейс при этом остаётся полностью
inline: после `/start` пользователь выбирает действие кнопками под
приветственным сообщением.

Для общего набора используется `BotCommandScopeDefault`. При `/start` и после
смены роли точный набор обновляется через `BotCommandScopeChat`. Поэтому
изменение SQLite-роли не требует restart. Ошибка обновления Telegram Commands
логируется и не откатывает сохранённую роль.

### User Commands

- `/start` — открыть главное меню;
- `/catalog` — открыть каталог;
- `/search` — начать поиск;
- `/help` — показать краткую справку;
- `/myid` — показать собственный Telegram ID;
- `/warehouse` — открыть списания и перемещения (только при включённом модуле
  и разрешённой роли).

### Admin Commands

- `/admin` — открыть административную панель;
- `/users` — открыть управление пользователями.

При выключенном warehouse accountant и blocked видят только `/start`, `/help`
и `/myid`. При включённом warehouse accountant дополнительно видит
`/warehouse`; bartender, admin и super_admin также получают эту команду, а
user и blocked — нет. User и bartender видят пользовательский набор; admin и
super_admin — пользовательский и административный. Для известных
привилегированных и ограниченных ролей при старте приложения регистрируются
отдельные `BotCommandScopeChat`.

Администратор также видит inline-кнопку «🛠 Управление каталогом» в главном
меню. `ReplyKeyboardMarkup` как основной интерфейс не используется.

## Формат `catalog.json`

Категория может содержать `items` непосредственно или использовать один
уровень `subcategories`. Названия разделов не прописываются в handlers или
клавиатурах.

```json
{
  "version": 1,
  "categories": [
    {
      "id": "coffee",
      "name": "Кофе",
      "emoji": "☕",
      "description": "Кофейная карта",
      "sort_order": 20,
      "is_active": true,
      "subcategories": [
        {
          "id": "hot-coffee",
          "name": "Горячий кофе",
          "emoji": "🔥",
          "description": null,
          "sort_order": 10,
          "is_active": true,
          "items": [
            {
              "id": "flat-white",
              "name": "Флэт уайт",
              "description": "Кофейный напиток с молоком",
              "photo_file_id": null,
              "ingredients": [
                {
                  "name": "Эспрессо",
                  "amount": 36,
                  "unit": "г"
                }
              ],
              "fields": {
                "cup": "200 мл",
                "coffee_weight": "18 г",
                "temperature": "65 °C"
              },
              "steps": [],
              "tags": [
                "кофейный"
              ],
              "sort_order": 10,
              "is_active": true
            }
          ]
        }
      ],
      "items": []
    }
  ]
}
```

Поле `subcategories` необязательно и по умолчанию пустое. Благодаря этому
старый формат с позициями непосредственно в `category.items` продолжает
работать.

`id` категории, подкатегории и позиции используются вместе в callback-данных.
Для гарантированного соблюдения лимита Telegram они должны:

- начинаться со строчной латинской буквы или цифры;
- содержать только `a-z`, `0-9`, `_` и `-`;
- иметь длину не более 18 символов;
- быть уникальными.

`sort_order` задаёт порядок. Записи с `is_active: false` не отображаются и не
участвуют в поиске. `fields` — произвольный JSON-объект для специфичных
характеристик любой категории.

Текущий каталог содержит 507 карточек в девяти основных разделах. Помимо
коктейлей, кофе и полуфабрикатов заполнены фирменные и классические чаи,
а также винная карта;
добавлены разделы барного алкоголя, безалкогольных напитков и десертов.
Фирменные авторские смеси отделены от классического листового и гречишного
чая. В «Фирменных коктейлях» сохранены 15 исходных карточек, а коктейли из
нового XLS-импорта вынесены в подраздел «Старые фирменные коктейли».
Аналогично восемь
исходных классических рецептов оставлены в «Классических коктейлях», а 15
импортированных — в «Старых классических коктейлях». Раздел также включает
безалкогольные и горячие позиции и пять шотов.
Вина разделены на белые, розовые, игристые и
красные. Барный алкоголь сгруппирован по типу, а лимонады, фреши, смузи,
бутылочные и домашние напитки находятся в отдельных подразделах. Разделы
остаются data-driven и не захардкожены в Python.

Каталог синхронизирован с актуальными файлами
`Технологическая_карта_полуфабрикати_бар.xls` и
`Технологическая карта бар блюда.xls`. Из них использовано 505 техкарт:
существующие карточки сопоставлялись по номеру техкарты и устойчивым
названиям, а их стабильные ID и фотографии сохранялись. Учётные дубли,
пяти-миллилитровые карты компонентов, себестоимостные копии и более старые
повторы одинакового объёма в публичный каталог не добавлялись. Килограммы и
литры приведены к граммам и миллилитрам; в `fields` сохранены номер, дата и
выход. Если XLS не содержал реальной технологии приготовления, шаги не
выдумывались.

Повторяемый импорт выполняет `source/import_bar_xls.py`: без параметров он
только строит и валидирует результат в памяти, а `--write` сохраняет каталог
через штатную атомарную запись с резервной копией. Старый текстовый источник
коктейлей находится в `source/tech_cards.txt`. Для 24 совпадающих исходных
коктейлей его состав имеет приоритет над XLS: в нём указаны конкретные вкусы
сиропов, ликёров, пюре и алкоголя. Номер, дата и выход при этом продолжают
обновляться из XLS. Неоднозначности прежнего импорта описаны в
`source/import_warnings.md`.

### `photo_file_id`

`photo_file_id` — идентификатор уже загруженной в Telegram фотографии, а не
локальный путь или URL. Если поле заполнено, бот отправляет фото и использует
карточку как caption, когда она помещается в лимит Telegram. Длинная карточка
отправляется отдельным сообщением. При недействительном `file_id` бот пишет
техническую ошибку в лог и показывает текстовую карточку.

Чтобы получить `file_id`, фотографию нужно один раз отправить Telegram-боту и
сохранить `file_id` из объекта сообщения.

## Управление каталогом

Админ-панель позволяет:

- создавать, редактировать, скрывать и подтверждённо удалять категории,
  подкатегории и позиции;
- редактировать название и описания карточки без изменения стабильного ID;
- полностью заменять ингредиенты, characteristics, шаги и теги;
- перемещать позиции между категориями и подкатегориями;
- просматривать активные, скрытые или все сущности;
- добавлять, заменять и подтверждённо удалять Telegram-фотографии.

При добавлении позиции администратор выбирает один из двух режимов:

- «🧩 Пошаговое создание» — прежний FSM-мастер с отдельным вводом каждого
  поля и фотографии;
- «📝 Создать по шаблону» — один заполненный текст для всей карточки после
  выбора категории или подкатегории.

До финального подтверждения `catalog.json` не изменяется. Опасные удаления
всегда требуют отдельного inline-подтверждения.

Администратор не вводит технические ID вручную. При создании категории,
подкатегории или позиции ID автоматически формируется из названия:
кириллица транслитерируется, а разделители приводятся к `snake_case`.
Например, «Джин-тоник юдзу» получает ID `gin_tonik_yuzu`, а
«Old Fashioned» — `old_fashioned`. Если такой ID уже занят в соответствующем
разделе, бот добавляет числовой суффикс: `_2`, `_3` и далее.

После создания технический ID не меняется при переименовании сущности и
используется только внутренней логикой, callback-данными, аудитом и будущими
ссылками. В интерфейсе он может отображаться информационно, но отдельного
редактирования ID нет.

### Формат ингредиентов

Одна строка — один ингредиент, ровно три части:

```text
Джин Finsbury | 45 | мл
Rancho Lime | 20 | мл
Easy Foam | 1 | dash
```

Ошибочные строки выводятся с номерами, частичный список не сохраняется.

### Формат характеристик

```text
glassware | Купе
ice | Без льда
method | Dry Shake → Shake
garnish | Маракуйя
```

Ключ должен быть уникальным lowercase ASCII `snake_case`, значение не может
быть пустым. Шаги вводятся по одному на строку. Теги вводятся через запятую;
пробелы и регистронезависимые дубли удаляются. Символ `-` очищает необязательное
поле или список.

### Редактирование через копирование

Telegram Bot API не позволяет боту автоматически заполнить обычное поле
ввода пользователя произвольным редактируемым текстом. Поэтому BarBot
показывает текущее значение без HTML-преобразований: администратор копирует
его, исправляет и отправляет обратно через удобный `ForceReply`.

Для отдельного поля значение показывается точно в формате его parser:
ингредиенты — по одному `Название | количество | единица` на строку,
характеристики — `ключ | значение`, шаги — по одному на строку, теги — через
запятую. Пустое необязательное значение показывается как `-`. Все прежние
кнопки редактирования отдельных полей остаются доступны.

Кнопка «📝 Редактировать карточку целиком» отправляет заполненный шаблон:

```text
НАЗВАНИЕ:
Kiss Me

КРАТКОЕ ОПИСАНИЕ:
-

ПОЛНОЕ ОПИСАНИЕ:
-

СОСТАВ:
Виски Pouges | 45 | мл

ХАРАКТЕРИСТИКИ:
glassware | Рокс

ПРИГОТОВЛЕНИЕ:
Перебить

ТЕГИ:
авторский, виски

ПОРЯДОК:
10

АКТИВНА:
да
```

Названия секций регистронезависимы и должны идти в показанном порядке.
Неизвестные и повторные секции запрещены. Активность принимает `да/нет`,
`true/false` или `1/0`, порядок — целое число. Parser сначала проверяет весь
шаблон и выводит все найденные ошибки; частичного сохранения нет. При
исправлении ошибочный текст показывается повторно, чтобы не начинать заново.

Полный шаблон намеренно не содержит стабильный ID, `photo_file_id`, категорию
или подкатегорию. При редактировании эти данные сохраняются, при создании ID
автоматически формируется существующим генератором, а фото предлагается
добавить отдельным шагом после подтверждения. Пошаговый режим и отдельное
редактирование фотографии сохранены.

Для текста длиной от 1 до 256 символов бот показывает системную кнопку
`CopyTextButton`. Она копирует значение в буфер, но не вставляет его в поле
ввода автоматически. Для более длинного текста кнопка не создаётся — нужно
использовать стандартное действие Telegram «Копировать»; текст при этом не
обрезается и не разбивается на несколько copy-кнопок.

### Фотографии

Изображение следует отправлять как Telegram Photo. Бот сохраняет только
вариант `file_id` максимального разрешения:

- файл не скачивается;
- URL и бинарные данные не сохраняются;
- document отклоняется;
- замена и удаление требуют предпросмотра/подтверждения;
- прежний текстовый fallback продолжает работать при недействительном ID.

## Warehouse backend foundation

Schema v3 добавила отдельный warehouse namespace в локальную SQLite:
locations, products, aliases, допустимые типы операций и singleton settings.
Rename сохраняет stable ID, updates используют optimistic revision check,
а official names и aliases находятся в едином нормализованном namespace.
Управлять справочником могут только `admin` и `super_admin`.

Schema v4 добавляет transactional foundation для смен, persistent intake
drafts, строк разрешения, fuzzy-кандидатов, складских операций и отдельного
warehouse audit. Business date рассчитывается в `Europe/Kyiv` с cutoff
`23:00`; количества хранятся целыми scaled values
(`1 base unit = 1_000_000`) и разбираются через `Decimal`, без `float`.

Schema v5 добавляет обязательные правила списаний, неизменяемый snapshot
требований конкретной смены и восстанавливаемые closing sessions. Правила
хранят ссылку на продукт, режим `recommended` или `manual`, расписание по
дням недели, подсказку количества, min/max и возможность отметить позицию
неприменимой. Физического удаления правил нет: администратор активирует или
деактивирует их, а изменения влияют только на новые смены.

Schema v6 добавляет `warehouse_reports` и `warehouse_report_lines` для
финальных XLSX. В SQLite хранится статус, версия, метаданные файла и
неизменяемый snapshot строк; сам XLSX остаётся на диске. Первая версия имеет
номер `v001`, готовый файл и строки готового отчёта не перезаписываются.

Schema v7 добавляет отдельный тип операции `development` («Проработка»),
snapshot-поле `development_title`, устойчивый `development_group_id` и
persistent draft для сообщения без названия. Replacement migration сохраняет
данные v6, пересоздаёт CHECK/FK/index/trigger и валидирует результат до commit.

Schema v8 добавляет `warehouse_report_recipients` с уникальным числовым
Telegram `chat_id`, soft activation и optimistic `revision`, а также
`warehouse_report_deliveries` с отдельным состоянием каждой отправки:
`pending`, `sending`, `delivered` или `failed`. Пара report/recipient уникальна,
поэтому повтор не создаёт новую доставку и не отправляет уже доставленный файл.

Schema v9 добавляет настраиваемые напоминания о незакрытой смене. Рабочий
Telegram chat ID отделён от бухгалтерских recipients; по умолчанию напоминания
выключены. Worker только напоминает: автоматическое закрытие, создание XLSX и
доставка по расписанию не реализованы. Production deployment не выполнялся.

Schema v10 добавляет расписания автоотправки уже готовых immutable XLSX:
ежедневные — от `scheduled_close_at_utc` смены с заданной задержкой, разовые —
для выбранного ready report. До ручного закрытия и появления ready report job
остаётся `waiting_report`; через 24 часа получает безопасный timeout. Закрытие
смены и генерация XLSX остаются ручными. Доставка повторяет только незавершённые
пары report/recipient и не пересоздаёт файл. Функция работает только при
`WAREHOUSE_ENABLED=true` (по умолчанию `false`); production deployment не
выполнялся.

Phase 8 включает создание и редактирование ежедневных и разовых расписаний,
изменение активных получателей и даты/времени разовой отправки с корректной
обработкой DST `Europe/Kyiv`. Повтор и отмена запуска требуют отдельного
подтверждения; бухгалтеру доступны карточки и история только для чтения.
Автоматическое закрытие смены по-прежнему отсутствует.

Schema v11 добавляет backend корректировок закрытой смены. Только
`super_admin` и `admin` могут провести смену по lifecycle
`closed → correction_open → closing → closed`, изменить операции под active
correction session и выпустить следующую immutable версию XLSX (`v002+`).
Исходные версии, snapshots и deliveries не перезаписываются; причина,
before/after и связь версий сохраняются в audit. Исправленная версия
отправляется только отдельным явным вызовом через существующий delivery flow.

Phase 9B.1 подключает Telegram UI открытия и редактирования active correction
из карточки актуального готового отчёта. `super_admin` и `admin` указывают
обязательную причину, подтверждают открытие, добавляют списания, перемещения и
проработки, редактируют операции через old → new preview, выполняют soft
delete/restore и просматривают diff относительно immutable base report.
Persistent session можно продолжить после потери FSM или перезапуска;
optimistic revision и повторная server-side проверка роли защищают все
mutation. `accountant` видит dashboard, операции и изменения только для
чтения. Отмена всей session разрешена лишь до первой mutation.

Phase 9B.2 завершает correction flow в Telegram: показывает diff и required
checklist перед подтверждением, выпускает следующую immutable XLSX-версию,
восстанавливает прерванную сборку, показывает цепочку `v001 → v002 → v003`,
позволяет выбрать активных получателей и явно отправить исправленный отчёт.
По умолчанию выбираются активные получатели успешной доставки base version;
если таких нет — все активные получатели. Доставки новой версии имеют
отдельные records, partial failure не откатывает успех, а retry повторяет
только failed и неактивных получателей безопасно пропускает. Correction reports
не подхватываются schedules и никогда не отправляются автоматически.
`accountant` видит correction dashboard, diff, причины, файлы, историю версий
и статусы доставок только для чтения; выпуск, выбор получателей, отправка и
retry доступны лишь `super_admin` и `admin`. Phase 9 завершена; production
migration и deployment в рамках разработки не выполнялись.

Phase 10A добавляет безопасный read-only preflight, migration/seed/offline-E2E
rehearsals и runbooks для backup, rollout и rollback. Target schema — v11.
Production deployment по-прежнему не выполнялся; Phase 10B допускается только
после отдельного явного разрешения владельца.

Policy различает безопасный default development и поэтапный controlled
production rollout. Ограниченный Stage 0 разрешает только read-only inspection;
Stage 1–4 требуют отдельных подтверждений и не наследуют разрешение предыдущего
этапа. Изменение policy не даёт права использовать новые разрешения в том же
turn. Первая попытка Stage 0 завершилась `NO-GO` без production mutations;
deployment всё ещё не выполнялся.

```bash
python -m app.release_preflight --config-check-only --polling-owner-count 1
```

Команда читает только process environment и не открывает `.env` сама; значения
секретов не выводятся. Полный порядок действий описан в
`docs/production_readiness.md`, `docs/production_rollout.md` и
`docs/production_rollback.md`.

Для отдельно разрешённого controlled Stage 0 preflight поддерживает
`--allow-supported-upgrade` (валидная v1–v10 становится предупреждением о
миграции после backup) и `--allow-missing-runtime-paths` (отсутствующий каталог
отчётов допустим только при выключенном warehouse). Approved backup root:
`/opt/barbot-backups/production`; новый timestamp target можно проверить через
`--backup-target`. Логический SQLite read-only не означает отсутствия
filesystem side effects: SQLite может создать или обновить `-wal`/`-shm`;
runtime sidecars игнорируются Git и не удаляются при работающем service.

Backend распознаёт только точные triggers первой непустой строки:

```text
списание: апельсин 0.15
перемещение:
морковь зачищ 0.33 кг

перемещение на кухню:
молоко 1 л

проработка: Новый облепиховый чай
облепиха 0.25 кг
сахарный сироп 0.15 л (баланс сладости)
```

Phase 4 добавляет отдельный Telegram router, inline-клавиатуры и FSM для
складских операций. Модуль выключен по умолчанию и подключается только при:

```dotenv
WAREHOUSE_ENABLED=true
```

Перед включением требуется schema v8, применяемая существующим migration
runner, и отдельный явный импорт warehouse seed. Startup не импортирует
номенклатуру и не создаёт products автоматически. Если модуль включён без
продуктов, бот показывает безопасное сообщение о неполной настройке.

Доступ:

- `super_admin`, `admin`, `bartender` — добавление, просмотр, исправление и
  soft delete операций текущей смены, прохождение обязательного checklist и
  подготовка смены к отчёту;
- `super_admin`, `admin` — дополнительно создание и изменение обязательных
  правил без физического удаления;
- `accountant` — только списки, агрегированные итоги и статус checklist;
- `user`, `blocked` — без кнопки, команды и доступа к данным warehouse.

Операцию можно начать inline-кнопкой либо свободным сообщением при отсутствии
другого активного FSM:

```text
списание: апельсин 0.15

перемещение:
морковь зачищ 0.33 кг

проработка: Новый малиновый чай
малина с/м 0.2 кг
сахарный сироп 0.15 л
```

Для перемещения место назначения выбирается отдельной inline-кнопкой для каждой
позиции. Быстрый формат `сахар 1 кг -> кухня` также поддерживается и не требует
повторного выбора. Поддерживаются несколько строк, необязательная основная
единица, причина или комментарий в скобках, явное разрешение fuzzy-вариантов,
исправление ошибочной строки и persistent recovery незавершённого batch. До подтверждения
операции не создаются. После подтверждения доступны записи текущей смены,
пагинация по 8, агрегированные итоги, optimistic edit и soft delete с audit.
Для проработки название обязательно и редактируется атомарно сразу во всей
группе операций одного сообщения. Сообщение `проработка:` с ингредиентами
сохраняется в SQLite и после restart продолжает сценарий запроса названия.
Заголовки `перемещение на <место>:` и `перемещение в <место>:` применяют
destination ко всем строкам; сочетание такого заголовка со стрелкой запрещено.

Неполную складскую строку можно дозаполнять по полям. Если продукт распознан, но
количество отсутствует, бот отдельно запрашивает количество (`0,5`, `500 мл`,
`0,5 л`) и не требует повторять название. Если название найдено приблизительно,
кандидаты показываются inline-кнопками: fuzzy-поиск никогда не выбирает продукт
автоматически. При уточнении названия уже распознанные количество, единица,
комментарий и направление сохраняются.

Кнопка «✅ Закрыть смену» сначала показывает сводку, затем последовательно
спрашивает только отсутствующие обязательные позиции. Быстрое подтверждение
рекомендации и ручное количество создают обычные операции с
`origin=required_rule`; они участвуют в общих итогах. Причина «Сегодня не
списывали» сохраняется в snapshot требования и transactional warehouse audit,
но не создаёт нулевую операцию. Незавершённый checklist можно продолжить
после перезапуска; отмена не удаляет уже сохранённые списания.
Операции `development` не выполняют required writeoff checklist: требования
закрывает только активная операция с точным типом `writeoff`.

Финальное подтверждение повторно пересчитывает требования и одной
`BEGIN IMMEDIATE`-транзакцией переводит смену в `closing`, завершает closing
session и пишет audit. В этом статусе обычные create/edit/delete заморожены.

После этого бот создаёт immutable snapshot, вне транзакции и event loop
формирует XLSX через XlsxWriter и атомарно публикует его в
`reports/warehouse/YYYY/MM/warehouse_YYYY-MM-DD_v001.xlsx`. Только после
проверки ZIP, размера и SHA-256 вторая транзакция переводит отчёт в `ready`,
а смену из `closing` в `closed`. При сбое смена остаётся замороженной в
`closing`; повтор использует тот же snapshot и версию. Состояния
`closing + building`, уже опубликованный корректный файл и
`ready + closing` восстанавливаются идемпотентно.

«📄 Скачать текущий Excel» строит временный draft из актуальных non-deleted
операций. Draft не закрывает смену, не создаёт версию и удаляется после
отправки. «📁 История отчётов» показывает только готовые отчёты по 8 на
странице. `accountant` может создавать draft, смотреть историю и скачивать
готовые файлы, но не может закрывать смену или формировать final. Для пустой
смены требуется отдельное подтверждение; итоговый workbook всё равно содержит
три листа с заголовками.

XLSX всегда содержит ровно листы «Списание», «Перемещение» и «Проработка» в
этом порядке. В третьем листе колонки: дата, название проработки, продукт,
количество, единица и комментарий. Одинаковый продукт суммируется только
внутри одного `development_group_id`; разные сообщения не объединяются даже
при одинаковом названии. Количества — числа, даты — Excel dates, текст пишется
без формул и URL-автоконвертации.
Технические ID, Telegram ID, имя бармена, raw messages и audit в отчёт не
включаются. Администратор регистрирует получателя из нужного текущего чата
либо вводит числовой `chat_id`; `@username` адресом доставки не считается.
Перед сохранением бот проверяет чат через Telegram API и доступность отправки
документов, но тестовый файл не посылает. После ручного закрытия один готовый
XLSX отправляется всем активным получателям. Успех и ошибка фиксируются
отдельно, частичная ошибка не откатывает закрытие, а явный retry повторяет
только failed/незавершённые доставки. Автоматическое закрытие смены не
реализовано. Исправленные версии выпускаются и доставляются только вручную;
schedules их не выбирают. Продукты из каталога автоматически в SQLite не
импортируются.

`WAREHOUSE_ENABLED` по-прежнему имеет безопасное значение по умолчанию
`false`. В рамках Phase 7 production migration, production seed import и
production deployment не выполнялись.

`source/warehouse_product_candidates.json` — автоматически извлечённый
материал для анализа, а не активная warehouse-номенклатура.

```bash
.venv/bin/python scripts/preview_warehouse_candidates.py \
  --catalog data/catalog.json \
  --output source/warehouse_product_candidates.json
```

Без `--output` утилита работает в read-only preview-режиме.

`source/warehouse_products_seed.json` — валидируемый утверждённый источник
начальной номенклатуры. Он детерминированно формируется из candidate report,
сохраняет все 412 извлечённых позиций и две отдельные owner-required позиции.
Все 414 продуктов активны; review status и warnings сохранены и не отключают
позиции. Каждый продукт поддерживает `writeoff`, `transfer` и `development`.
Ни candidate report, ни seed сами по себе не изменяют SQLite.

Повторная генерация seed:

```bash
.venv/bin/python scripts/generate_warehouse_product_seed.py \
  --input source/warehouse_product_candidates.json \
  --output source/warehouse_products_seed.json
```

Импорт поддерживает подготовленную schema v3/v4/v5/v6/v7/v8 и требует обязательный путь
к базе. Без
`--apply` команда только валидирует seed и показывает план:

```bash
.venv/bin/python scripts/import_warehouse_products.py \
  --database /path/to/test.db \
  --input source/warehouse_products_seed.json
```

Запись выполняется только с явным `--apply`, одним атомарным batch. Повторный
импорт идентичного seed возвращает `unchanged`; расхождение stable ID или
единого namespace вызывает полный отказ без частичных updates. Production DB
не является значением по умолчанию и дополнительно запрещена CLI.
Автоматического импорта при startup нет.

На schema v5/v6/v7/v8 тот же атомарный импорт создаёт два owner-required правила:

- «Молотый кофе из гриндера» — ежедневно, рекомендовано `0,06 кг`;
- «Остаток молока в питчерах» — ежедневно, ручной ввод в литрах.

Повторный импорт показывает оба правила как `rule_unchanged`; несовпадение
существующего правила является конфликтом и откатывает импорт целиком.

## Пользователи и SQLite

`data/barbot.db` создаётся безопасно при старте. Используется стандартный
`sqlite3`, WAL, `foreign_keys=ON`, `busy_timeout` и `PRAGMA user_version`.
Единственный versioned migration runner создаёт новую базу сразу как schema
v8, атомарно обновляет прежние последовательности через v4 → v5 → v6 → v7 → v8 и
отклоняет неизвестную будущую либо несогласованную схему. Каждый migration
step имеет отдельную транзакцию; повторная инициализация v8 только валидирует
данные.
ORM, PostgreSQL, Redis и общая удалённая база не используются.

Таблица `users` хранит Telegram ID как стабильный ключ, профиль Telegram,
роль, статус, первый/последний вход, автора назначения, время обновления и
признак первого `/start`. При каждом взаимодействии профиль и
`last_seen_at` обновляются, но роль никогда не сбрасывается. Username может
изменяться или отсутствовать и не используется как идентификатор.

```text
telegram_user_id INTEGER PRIMARY KEY
username / first_name / last_name TEXT NULL
role TEXT: admin | bartender | accountant | user | blocked
is_active INTEGER
first_seen_at / last_seen_at / updated_at TEXT
created_by INTEGER NULL
has_started INTEGER
```

### Управление ролями

В административной панели есть «👥 Управление пользователями»: списки с
пагинацией, локальный поиск, карточка пользователя, назначение ролей,
блокировка и разблокировка. Каждое изменение требует отдельного inline-
подтверждения и записывается в административный JSONL-аудит.

Основное добавление сотрудника использует временную системную
`KeyboardButtonRequestUsers` с выбором одного не-бота. После выбора или
отмены клавиатура удаляется через `ReplyKeyboardRemove`; постоянной reply-
клавиатуры нет. Telegram может не передать username, и бот не умеет искать
произвольного человека глобально по `@username`.

Альтернативный сценарий «📋 Выбрать из пользователей бота» и поиск работают
только по локальной SQLite. Если сотрудник ещё не запускал бота, роль можно
сохранить по выбранному Telegram ID, но бот не пишет ему первым: сотрудника
нужно попросить самостоятельно открыть бота и нажать `/start`.

## Безопасность записи

Каждая успешная мутация выполняется под общим `asyncio.Lock`:

1. загружается актуальный файл;
2. меняется и повторно валидируется Pydantic-модель;
3. текущий файл копируется в `backups/catalog/`;
4. новый JSON записывается во временный файл с `flush` и `fsync`;
5. `os.replace` атомарно заменяет каталог;
6. сохранённый файл перечитывается и валидируется.

Хранится не более 30 backups с именами
`catalog-YYYYMMDD-HHMMSS-ffffff.json`.

Административный аудит записывается в `logs/admin_audit.jsonl`: UTC-время,
ID администратора, username при наличии, действие, тип/ID сущности,
родительские ID, описание и статус. Токен, `.env`, полные Telegram updates и
бинарные фотографии туда не попадают. Ошибка аудита логируется, но не
откатывает уже валидно сохранённый каталог.

Тот же журнал получает безопасные события `user_registered`, `role_changed`,
`user_blocked`, `user_unblocked` и `role_change_denied` без `.env`, токена,
полных updates или личных сообщений.

## Резервное копирование и новый ресторан

Автоматические backups по-прежнему создаются только для `catalog.json`.
SQLite на этом этапе не имеет отдельной автоматической ротации, поэтому
владелец должен включить `data/barbot.db` в резервное копирование VPS.

Новый ресторан — отдельный экземпляр бота: тот же Python-код, новый
`BOT_TOKEN`, новый `SUPER_ADMIN_IDS`, отдельные `catalog.json`, пустая
`barbot.db`, backups и audit. Базы разных ресторанов не объединяются.

## Поведение и ограничения

- нет избранного и статистики;
- `data/users.json` не используется;
- нет ORM, Redis, PostgreSQL, webhook или web-панели;
- после административного или ручного изменения `catalog.json` данные
  перечитываются при следующем пользовательском запросе;
- поддерживается ровно один уровень подкатегорий;
- при синтаксической ошибке или невалидной структуре каталог временно
  недоступен до исправления файла.

После изменения данных restart не требуется. После изменения Python-кода или
`.env` процесс/systemd нужно перезапустить.
