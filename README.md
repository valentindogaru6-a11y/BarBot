# BarBot

BarBot — Telegram-справочник для сотрудников бара. Категории и позиции
полностью формируются из `data/catalog.json`: новую категорию, напиток,
десерт или рабочий стандарт можно добавить без изменения Python-кода.

Текущая версия использует Python 3.12, aiogram 3 и Telegram long polling.
Каталог хранится в JSON и валидируется Pydantic. Пользователи и изменяемые
роли хранятся в локальной SQLite, а владельцы экземпляра задаются по
Telegram user ID через окружение.

## Возможности

- главное inline-меню: «📚 Каталог» и «🔍 Поиск»;
- динамические категории, подкатегории и позиции;
- один необязательный уровень подкатегорий с сортировкой и `is_active`;
- пагинация по 8 элементов;
- универсальные карточки с составом, характеристиками, шагами и тегами;
- отправка фотографии по Telegram `file_id`;
- поиск по названию, описаниям, тегам и ингредиентам;
- FSM-диалог поиска с командой `/cancel` и inline-отменой;
- роли `super_admin`, `admin`, `bartender`, `user` и `blocked`;
- локальная SQLite-база пользователей и управление ролями;
- защищённая Telegram-админка для каталога, текстов и фотографий;
- атомарная запись, резервные копии и JSONL-аудит;
- понятные сообщения при ошибках файла или структуры каталога.

## Архитектура

```text
data/catalog.json          data/barbot.db
       ↓                         ↓
JSON storage              SQLite user storage
       └──────────┬──────────────┘
                  ↓
app/models → app/services → app/handlers → app/keyboards
```

Основные каталоги:

- `app/models/` — модели каталога, пользователей и ролей;
- `app/storage/` — JSON-каталог и SQLite без ORM;
- `app/services/` — каталог, поиск, авторизация, CRUD и аудит;
- `app/handlers/` — пользовательские сценарии и разделённый пакет `admin/`;
- `app/keyboards/` — пользовательские и административные callbacks/клавиатуры;
- `app/utils/` — нормализация и безопасное HTML-форматирование;
- `data/catalog.json` — данные каталога;
- `tests/` — тесты без обращений к Telegram API.

`data/users.json` не используется и оставлен только как deprecated-файл.
Источник пользователей и изменяемых ролей — `data/barbot.db`.

## Создание Telegram-бота

1. Откройте официальный аккаунт `@BotFather` в Telegram.
2. Выполните команду `/newbot`.
3. Укажите отображаемое имя и уникальное имя, оканчивающееся на `bot`.
4. Сохраните выданный токен. Не публикуйте его и не добавляйте в Git.

## Установка

```bash
cd /opt/barbot
python3.12 -m venv .venv
source .venv/bin/activate
python -m pip install -r requirements.txt
```

## Настройка `.env`

Скопируйте безопасный пример:

```bash
cp .env.example .env
```

Заполните значения:

```dotenv
BOT_TOKEN=replace_with_your_telegram_bot_token
CATALOG_PATH=data/catalog.json
DATABASE_PATH=data/barbot.db
SUPER_ADMIN_IDS=[123456789,987654321]
```

- `BOT_TOKEN` обязателен.
- `CATALOG_PATH` необязателен и по умолчанию указывает на
  `/opt/barbot/data/catalog.json`.
- Относительный `CATALOG_PATH` всегда вычисляется от корня проекта, поэтому
  запуск не зависит от текущей рабочей директории.
- `DATABASE_PATH` по умолчанию равен `/opt/barbot/data/barbot.db` и также
  вычисляется от корня проекта.
- `SUPER_ADMIN_IDS` — необязательный JSON-массив положительных Telegram ID.
  Для production рекомендуется указать минимум одного владельца.
- Если `SUPER_ADMIN_IDS` не задан, старый `ADMIN_IDS` временно используется
  как bootstrap владельцев. Это deprecated-совместимость; предупреждение
  пишется без вывода самих ID.

Настоящий `.env` исключён из Git.

## Роли и безопасность

- `super_admin` задаётся только через `SUPER_ADMIN_IDS`, имеет все права,
  назначает и снимает `admin` и не может быть изменён через бота;
- `admin` управляет каталогом и пользователями, назначает `bartender`,
  меняет `user/bartender/blocked`, но не управляет admin/super_admin и собой;
- `bartender` использует каталог и поиск без административных функций;
- `user` имеет обычный доступ к каталогу и поиску;
- `blocked` видит только сообщение об ограничении, `/help` и `/myid`.

Разрешения вычисляются централизованно и повторно проверяются перед сменой
роли. Super Admin не хранится как изменяемая SQLite-роль и потому не может
быть понижен или заблокирован через Telegram.

Узнать собственный Telegram ID можно командой:

```text
/myid
```

Добавьте полученное число в `.env`, например:

```dotenv
SUPER_ADMIN_IDS=[123456789,987654321]
```

Не используйте username, имя или номер телефона вместо ID. Проверка прав
выполняется не только при построении меню, но и в каждом административном
callback, message handler и FSM-шаге. Прямая попытка открыть callback
возвращает «Недостаточно прав».

После изменения `.env` требуется restart процесса/systemd. Настоящие ID не
следует добавлять в README или `.env.example`.

## Запуск

Активируйте виртуальное окружение и запустите:

```bash
source .venv/bin/activate
python -m app.bot
```

При запуске бот отключает webhook без удаления накопившихся обновлений и
переходит в long polling.

## Telegram Commands

При запуске бот регистрирует официальные Bot Commands и включает встроенную
кнопку команд Telegram. Основной интерфейс при этом остаётся полностью
inline: после `/start` пользователь выбирает действие кнопками под
приветственным сообщением.

Для общего набора используется `BotCommandScopeDefault`. При `/start` и после
смены роли точный набор обновляется через `BotCommandScopeChat`. Поэтому
изменение SQLite-роли не требует restart. Ошибка обновления Telegram Commands
логируется и не откатывает сохранённую роль.

### User Commands

- `/start` — открыть главное меню;
- `/catalog` — открыть каталог;
- `/search` — начать поиск;
- `/help` — показать краткую справку;
- `/myid` — показать собственный Telegram ID.

### Admin Commands

- `/admin` — открыть административную панель;
- `/users` — открыть управление пользователями.

Blocked видит только `/start`, `/help` и `/myid`. User и bartender видят
пользовательский набор; admin и super_admin — пользовательский и
административный.

Администратор также видит inline-кнопку «🛠 Управление каталогом» в главном
меню. `ReplyKeyboardMarkup` как основной интерфейс не используется.

## Формат `catalog.json`

Категория может содержать `items` непосредственно или использовать один
уровень `subcategories`. Названия разделов не прописываются в handlers или
клавиатурах.

```json
{
  "version": 1,
  "categories": [
    {
      "id": "coffee",
      "name": "Кофе",
      "emoji": "☕",
      "description": "Кофейная карта",
      "sort_order": 20,
      "is_active": true,
      "subcategories": [
        {
          "id": "hot-coffee",
          "name": "Горячий кофе",
          "emoji": "🔥",
          "description": null,
          "sort_order": 10,
          "is_active": true,
          "items": [
            {
              "id": "flat-white",
              "name": "Флэт уайт",
              "description": "Кофейный напиток с молоком",
              "photo_file_id": null,
              "ingredients": [
                {
                  "name": "Эспрессо",
                  "amount": 36,
                  "unit": "г"
                }
              ],
              "fields": {
                "cup": "200 мл",
                "coffee_weight": "18 г",
                "temperature": "65 °C"
              },
              "steps": [],
              "tags": [
                "кофейный"
              ],
              "sort_order": 10,
              "is_active": true
            }
          ]
        }
      ],
      "items": []
    }
  ]
}
```

Поле `subcategories` необязательно и по умолчанию пустое. Благодаря этому
старый формат с позициями непосредственно в `category.items` продолжает
работать.

`id` категории, подкатегории и позиции используются вместе в callback-данных.
Для гарантированного соблюдения лимита Telegram они должны:

- начинаться со строчной латинской буквы или цифры;
- содержать только `a-z`, `0-9`, `_` и `-`;
- иметь длину не более 18 символов;
- быть уникальными.

`sort_order` задаёт порядок. Записи с `is_active: false` не отображаются и не
участвуют в поиске. `fields` — произвольный JSON-объект для специфичных
характеристик любой категории.

Текущий каталог содержит «Коктейли» с четырьмя подкатегориями и 24
технологическими картами, а также пустые активные разделы «Полуфабрикаты»,
«Фирменные чаи», «Кофейная карта» и «Винная карта». Разделы остаются
data-driven и не захардкожены в Python. Исходник коктейлей находится в
`source/tech_cards.txt`, неоднозначности — в `source/import_warnings.md`.

### `photo_file_id`

`photo_file_id` — идентификатор уже загруженной в Telegram фотографии, а не
локальный путь или URL. Если поле заполнено, бот отправляет фото и использует
карточку как caption, когда она помещается в лимит Telegram. Длинная карточка
отправляется отдельным сообщением. При недействительном `file_id` бот пишет
техническую ошибку в лог и показывает текстовую карточку.

Чтобы получить `file_id`, фотографию нужно один раз отправить Telegram-боту и
сохранить `file_id` из объекта сообщения.

## Управление каталогом

Админ-панель позволяет:

- создавать, редактировать, скрывать и подтверждённо удалять категории,
  подкатегории и позиции;
- редактировать название и описания карточки без изменения стабильного ID;
- полностью заменять ингредиенты, characteristics, шаги и теги;
- перемещать позиции между категориями и подкатегориями;
- просматривать активные, скрытые или все сущности;
- добавлять, заменять и подтверждённо удалять Telegram-фотографии.

При добавлении позиции администратор выбирает один из двух режимов:

- «🧩 Пошаговое создание» — прежний FSM-мастер с отдельным вводом каждого
  поля и фотографии;
- «📝 Создать по шаблону» — один заполненный текст для всей карточки после
  выбора категории или подкатегории.

До финального подтверждения `catalog.json` не изменяется. Опасные удаления
всегда требуют отдельного inline-подтверждения.

Администратор не вводит технические ID вручную. При создании категории,
подкатегории или позиции ID автоматически формируется из названия:
кириллица транслитерируется, а разделители приводятся к `snake_case`.
Например, «Джин-тоник юдзу» получает ID `gin_tonik_yuzu`, а
«Old Fashioned» — `old_fashioned`. Если такой ID уже занят в соответствующем
разделе, бот добавляет числовой суффикс: `_2`, `_3` и далее.

После создания технический ID не меняется при переименовании сущности и
используется только внутренней логикой, callback-данными, аудитом и будущими
ссылками. В интерфейсе он может отображаться информационно, но отдельного
редактирования ID нет.

### Формат ингредиентов

Одна строка — один ингредиент, ровно три части:

```text
Джин Finsbury | 45 | мл
Rancho Lime | 20 | мл
Easy Foam | 1 | dash
```

Ошибочные строки выводятся с номерами, частичный список не сохраняется.

### Формат характеристик

```text
glassware | Купе
ice | Без льда
method | Dry Shake → Shake
garnish | Маракуйя
```

Ключ должен быть уникальным lowercase ASCII `snake_case`, значение не может
быть пустым. Шаги вводятся по одному на строку. Теги вводятся через запятую;
пробелы и регистронезависимые дубли удаляются. Символ `-` очищает необязательное
поле или список.

### Редактирование через копирование

Telegram Bot API не позволяет боту автоматически заполнить обычное поле
ввода пользователя произвольным редактируемым текстом. Поэтому BarBot
показывает текущее значение без HTML-преобразований: администратор копирует
его, исправляет и отправляет обратно через удобный `ForceReply`.

Для отдельного поля значение показывается точно в формате его parser:
ингредиенты — по одному `Название | количество | единица` на строку,
характеристики — `ключ | значение`, шаги — по одному на строку, теги — через
запятую. Пустое необязательное значение показывается как `-`. Все прежние
кнопки редактирования отдельных полей остаются доступны.

Кнопка «📝 Редактировать карточку целиком» отправляет заполненный шаблон:

```text
НАЗВАНИЕ:
Kiss Me

КРАТКОЕ ОПИСАНИЕ:
-

ПОЛНОЕ ОПИСАНИЕ:
-

СОСТАВ:
Виски Pouges | 45 | мл

ХАРАКТЕРИСТИКИ:
glassware | Рокс

ПРИГОТОВЛЕНИЕ:
Перебить

ТЕГИ:
авторский, виски

ПОРЯДОК:
10

АКТИВНА:
да
```

Названия секций регистронезависимы и должны идти в показанном порядке.
Неизвестные и повторные секции запрещены. Активность принимает `да/нет`,
`true/false` или `1/0`, порядок — целое число. Parser сначала проверяет весь
шаблон и выводит все найденные ошибки; частичного сохранения нет. При
исправлении ошибочный текст показывается повторно, чтобы не начинать заново.

Полный шаблон намеренно не содержит стабильный ID, `photo_file_id`, категорию
или подкатегорию. При редактировании эти данные сохраняются, при создании ID
автоматически формируется существующим генератором, а фото предлагается
добавить отдельным шагом после подтверждения. Пошаговый режим и отдельное
редактирование фотографии сохранены.

Для текста длиной от 1 до 256 символов бот показывает системную кнопку
`CopyTextButton`. Она копирует значение в буфер, но не вставляет его в поле
ввода автоматически. Для более длинного текста кнопка не создаётся — нужно
использовать стандартное действие Telegram «Копировать»; текст при этом не
обрезается и не разбивается на несколько copy-кнопок.

### Фотографии

Изображение следует отправлять как Telegram Photo. Бот сохраняет только
вариант `file_id` максимального разрешения:

- файл не скачивается;
- URL и бинарные данные не сохраняются;
- document отклоняется;
- замена и удаление требуют предпросмотра/подтверждения;
- прежний текстовый fallback продолжает работать при недействительном ID.

## Пользователи и SQLite

`data/barbot.db` создаётся безопасно при старте. Используется стандартный
`sqlite3`, WAL, `foreign_keys=ON`, `busy_timeout` и `PRAGMA user_version`.
ORM, PostgreSQL, Redis и общая удалённая база не используются.

Таблица `users` хранит Telegram ID как стабильный ключ, профиль Telegram,
роль, статус, первый/последний вход, автора назначения, время обновления и
признак первого `/start`. При каждом взаимодействии профиль и
`last_seen_at` обновляются, но роль никогда не сбрасывается. Username может
изменяться или отсутствовать и не используется как идентификатор.

```text
telegram_user_id INTEGER PRIMARY KEY
username / first_name / last_name TEXT NULL
role TEXT: admin | bartender | user | blocked
is_active INTEGER
first_seen_at / last_seen_at / updated_at TEXT
created_by INTEGER NULL
has_started INTEGER
```

### Управление ролями

В административной панели есть «👥 Управление пользователями»: списки с
пагинацией, локальный поиск, карточка пользователя, назначение ролей,
блокировка и разблокировка. Каждое изменение требует отдельного inline-
подтверждения и записывается в административный JSONL-аудит.

Основное добавление сотрудника использует временную системную
`KeyboardButtonRequestUsers` с выбором одного не-бота. После выбора или
отмены клавиатура удаляется через `ReplyKeyboardRemove`; постоянной reply-
клавиатуры нет. Telegram может не передать username, и бот не умеет искать
произвольного человека глобально по `@username`.

Альтернативный сценарий «📋 Выбрать из пользователей бота» и поиск работают
только по локальной SQLite. Если сотрудник ещё не запускал бота, роль можно
сохранить по выбранному Telegram ID, но бот не пишет ему первым: сотрудника
нужно попросить самостоятельно открыть бота и нажать `/start`.

## Безопасность записи

Каждая успешная мутация выполняется под общим `asyncio.Lock`:

1. загружается актуальный файл;
2. меняется и повторно валидируется Pydantic-модель;
3. текущий файл копируется в `backups/catalog/`;
4. новый JSON записывается во временный файл с `flush` и `fsync`;
5. `os.replace` атомарно заменяет каталог;
6. сохранённый файл перечитывается и валидируется.

Хранится не более 30 backups с именами
`catalog-YYYYMMDD-HHMMSS-ffffff.json`.

Административный аудит записывается в `logs/admin_audit.jsonl`: UTC-время,
ID администратора, username при наличии, действие, тип/ID сущности,
родительские ID, описание и статус. Токен, `.env`, полные Telegram updates и
бинарные фотографии туда не попадают. Ошибка аудита логируется, но не
откатывает уже валидно сохранённый каталог.

Тот же журнал получает безопасные события `user_registered`, `role_changed`,
`user_blocked`, `user_unblocked` и `role_change_denied` без `.env`, токена,
полных updates или личных сообщений.

## Резервное копирование и новый ресторан

Автоматические backups по-прежнему создаются только для `catalog.json`.
SQLite на этом этапе не имеет отдельной автоматической ротации, поэтому
владелец должен включить `data/barbot.db` в резервное копирование VPS.

Новый ресторан — отдельный экземпляр бота: тот же Python-код, новый
`BOT_TOKEN`, новый `SUPER_ADMIN_IDS`, отдельные `catalog.json`, пустая
`barbot.db`, backups и audit. Базы разных ресторанов не объединяются.

- нет ORM, Redis, PostgreSQL, webhook или web-панели;
- после административного или ручного изменения `catalog.json` данные
  перечитываются при следующем пользовательском запросе;
- поддерживается ровно один уровень подкатегорий;
- при синтаксической ошибке или невалидной структуре каталог временно
  недоступен до исправления файла.

После изменения данных restart не требуется. После изменения Python-кода или
`.env` процесс/systemd нужно перезапустить.
